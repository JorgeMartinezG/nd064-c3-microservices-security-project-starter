PART 1: DOCKER ENVIRONMENT ATTACK SURFACES (5 Observations)
----------------------------------------------------------------------

Observation 1:
- Component: Container Runtime / Process Privileges
- STRIDE Pillar: Elevation of Privilege
- Description: By default, containers run processes as the 'root' user inside the container namespace. If a malicious actor successfully exploits a code flaw in the Python Flask application, they will immediately inherit root privileges inside that container. This significantly lowers the barrier for executing container breakout techniques to attack the host kernel via malicious system calls.

Observation 2:
- Component: Docker Daemon Socket Configuration
- STRIDE Pillar: Tampering
- Description: The Docker daemon socket (/var/run/docker.sock) is the main management interface for Docker. If this socket is inadvertently exposed, mounted inside a container, or left with insecure permissions, an attacker who gains access to it can send direct API commands to the daemon. This allows them to spin up unauthorized, highly privileged containers that can tamper with the underlying host system.

Observation 3:
- Component: Environment Variables and Image Layer Storage
- STRIDE Pillar: Information Disclosure
- Description: Hardcoding production secrets, API keys, or database credentials directly into the Dockerfile instructions (or passing them as plain text environment variables) creates a major vulnerability. Any user with access to the container image registry or the local host can run 'docker inspect' or use image history tools to recover these sensitive credentials.

Observation 4:
- Component: Host Resource Allocation and Constraints
- STRIDE Pillar: Denial of Service (DoS)
- Description: Launching the Python Flask container without explicitly restricting its CPU and memory usage flags (--memory and --cpus) allows it to consume unrestricted host resources. If the application experiences an intense traffic spike, a memory leak, or a malicious resource-exhaustion attack, it could destabilize the entire OpenSUSE host machine, knocking down all other co-located infrastructure.

Observation 5:
- Component: Daemon Logging and Audit Subsystem
- STRIDE Pillar: Repudiation
- Description: Insufficient configuration of persistent and central logging within the Docker daemon (/etc/docker/daemon.json) hinders traceability. If a threat actor gains unauthorized access, alters container states, or injects malicious binaries, the lack of tamper-proof, immutable historical logs allows them to erase their actions, preventing security analysts from conducting effective incident response or forensic investigations.

PART 2: KUBERNETES ENVIRONMENT ATTACK SURFACES (5 Observations)
----------------------------------------------------------------------

Observation 6:
- Component: Kubernetes API Server Access Control
- STRIDE Pillar: Elevation of Privilege / Spoofing
- Description: The kube-apiserver is the central administrative gateway for the entire RKE cluster. If the Role-Based Access Control (RBAC) policies are overly permissive or cluster-admin privileges are loosely assigned, a compromised service account token from a web-facing pod can allow an attacker to spoof administrative roles and gain full operational control over the cluster plane.

Observation 7:
- Component: etcd Cluster Datastore Cifrado
- STRIDE Pillar: Information Disclosure / Tampering
- Description: The etcd key-value store contains the complete state, configurations, and secrets of the Kubernetes cluster. If etcd does not enforce mutual TLS (mTLS) for all incoming connections, or if Secrets are stored in plain text without encryption-at-rest configured, an attacker compromising the node network can read administrative tokens or tamper with the cluster database directly.

Observation 8:
- Component: Kubelet API Endpoint Security
- STRIDE Pillar: Tampering
- Description: The Kubelet daemon runs on the worker node to execute instructions from the control plane. If the Kubelet port (10250) is configured to accept unauthenticated, anonymous requests, an attacker with network access to the worker node can bypass the main API Server completely and inject malicious commands or execute arbitrary payloads directly into the running application pods.

Observation 9:
- Component: Cluster Flat Network Architecture (Pod-to-Pod)
- STRIDE Pillar: Information Disclosure / Denial of Service (DoS)
- Description: By default, Kubernetes networking allows every pod to communicate with every other pod across the entire cluster without restrictions. If the vulnerable Python Flask application pod is compromised, an attacker can use it as a launchpad for unrestricted lateral movement, scanning the cluster network to discover internal management components or flooding the API Server with internal traffic.

Observation 10:
- Component: Pod Security Standards and Runtime Namespaces
- STRIDE Pillar: Elevation of Privilege
- Description: Allowing pods to deploy with host-level privileges (such as hostNetwork: true, hostPID: true, or privileged: true) completely bypasses container isolation boundaries. An attacker exploiting the vulnerable Flask application inside a privileged pod can directly view and interact with the host operating system's kernel, leading to an immediate and total compromise of the entire underlying OpenSUSE worker node.

PART 3: DOCKER-BENCH RUN RESULTS AND ANALYSIS (3 Hardened Findings)
----------------------------------------------------------------------

Finding 1 (CIS Item 4.1 - Ensure a user for the container has been created):
- Target Attack Surface: Observation 1 (Elevation of Privilege / Process Privileges)
- Justification: Out of the box, Docker-bench reports that the container runs as root. Hardening this weakness by adding a non-root user (e.g., 'USER appuser') in the Dockerfile directly addresses the Elevation of Privilege threat, ensuring that if the Flask app is compromised, the attacker does not get root access to the system.

Finding 2 (CIS Item 5.12 - Ensure mount propagation mode is not set to shared):
- Target Attack Surface: Observation 2 (Tampering / Docker Daemon & Host Volumes)
- Justification: A shared mount propagation could allow a container to tamper with volume mounts on the host system. Ensuring this is restricted prevents unauthorized modifications from inside the container to the host filesystem, reducing the risk of host-level configuration tampering.

Finding 3 (CIS Item 5.11 - Ensure that the desired cgroup-parent is modified only with reason):
- Target Attack Surface: Observation 4 (Denial of Service / Resource Allocation)
- Justification: Leaving cgroups default or misconfigured allows a single container to exhaust host resources if restrictions are omitted. Implementing explicit control groups and resource limits constraints ensures that a compromised application cannot induce a Denial of Service attack against the entire host system.
